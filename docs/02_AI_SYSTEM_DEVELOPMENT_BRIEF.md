# beNeCare — AI System Development Brief

เอกสารคำสั่งพัฒนาระบบสำหรับ AI (หรือทีมพัฒนา) ใช้สั่งสร้างระบบดูแลลูกค้าประกันกลุ่มผ่าน LINE OA ให้ชัดเจน ครอบคลุมฟังก์ชัน หน้าจอ ผู้ใช้งาน ฐานข้อมูล Workflow AI LINE OA Admin Security และเกณฑ์ตรวจรับงาน

**ระบบ:** beNeCare — Group Insurance Customer Care Platform  
**เทคโนโลยีหลัก:** Next.js (App Router), TypeScript, Tailwind CSS, MariaDB  
**รูปแบบติดตั้ง:** มี Installer ครั้งแรก (First-time Setup Wizard) และส่วนอัปเกรดอยู่ในเมนูการตั้งค่าของระบบ  
**ภาษาเอกสาร:** ไทย (ศัพท์เทคนิคเป็นอังกฤษ)

---

## 1. ภาพรวมโครงการและเป้าหมาย

### 1.1 วัตถุประสงค์
สร้างระบบดูแลลูกค้าประกันกลุ่ม ผ่าน LINE OA ตอบคำถามได้ตลอด 24 ชั่วโมง แยกข้อมูลแต่ละบริษัทออกจากกัน (Multi-tenant) รองรับองค์กรขนาดใหญ่สูงสุด 5,000 คนต่อบริษัท และกลุ่มขนาดกลาง 100–1,000 คน เริ่มติดตั้งระบบช่วงต้นปี พร้อมวางพื้นฐานให้เชื่อมต่อกับระบบของ AIA ในอนาคต

### 1.2 หลักการสำคัญ (ข้อห้ามเด็ดขาด)
- **ห้าม AI หรือทีมพัฒนาสร้างฟังก์ชันหรือการเชื่อมต่อที่ยังไม่มีสิทธิ์ใช้งานขึ้นมาเอง** โดยเฉพาะการเชื่อมต่อ API / ข้อมูล / โลโก้ / ชื่อ ของ AIA
- รายการใดที่ยังต้องยืนยันกับ AIA ให้อยู่ในส่วน "3.2 สิ่งที่ต้องยืนยันกับ AIA (ยังห้ามสร้าง)" เท่านั้น ไม่อนุญาตให้ถูกสร้างเป็นโค้ดจริงจนกว่าจะมีเอกสารยืนยันจาก AIA
- ระบบต้องแยกข้อมูลแต่ละบริษัทอย่างชัดเจน ข้อมูลของบริษัท A ห้ามมองเห็นโดยบริษัท B เด็ดขาด

## 2. สิ่งที่ยืนยันแล้ว — ข้อกำหนดของระบบ (ให้ AI สร้างได้ทันที)

ส่วนนี้คือข้อกำหนดที่ชัดเจนแล้ว ให้ AI สร้างระบบตามนี้ได้เลย

### 2.1 เทคโนโลยี (Tech Stack)
| ชั้น | เทคโนโลยี | หมายเหตุ |
|---|---|---|
| Frontend | Next.js 14+ (App Router), TypeScript, Tailwind CSS | รองรับ SSR/SSG, Mobile-first |
| UI Kit | Headless UI / Radix + Tailwind | คอมโพเนนต์ฟอร์ม ตาราง มอดอล |
| Backend | Next.js API Routes / Server Actions | รันบน Node.js |
| Database | MariaDB 10.6+ | ผ่าน Prisma ORM หรือ Drizzle ORM |
| Cache / Session | Redis (ตัวเลือก) หรือ database session | สำหรับ access token LINE OA แคชระยะสั้น |
| LINE | LINE Messaging API (Official Account) | Webhook, Rich Menu, Broadcast |
| AI | OpenAI API / Azure OpenAI หรือโมเดลภาษาไทยที่เลือก | Intent classification, FAQ answer |
| Installer | Node.js script ภายใน Next.js | วิซาร์ดตั้งค่าครั้งแรก |
| Deployment | Docker หรือ standalone build | เลือกตามโครงสร้างของลูกค้า |

### 2.2 สถาปัตยกรรมฐานข้อมูล (MariaDB) และ Multi-tenancy

**โมเดลแยกข้อมูล:** ใช้ฐานข้อมูลกลางเดียวกัน แยกข้อมูลแต่ละบริษัทโดยคอลัมน์ `company_id` ทุกตารางธุรกิจ (บันทึกแชต, พนักงาน, การแจ้งเตือน ฯลฯ) ต้องมี `company_id` และทุกคำถาม SQL ต้องกรองด้วย `company_id` เสมอ

**เงื่อนไขการขยาย:** อนุญาตให้ออกแบบให้รองรับการแยกฐานข้อมูลแยกต่างหากต่อบริษัทขนาดใหญ่ (ต่อไปในอนาคต) โดยไม่ต้องเขียนโค้ดใหม่ทั้งหมด — แต่เฟสแรกให้ใช้ `company_id` ในฐานข้อมูลร่วม

**ตารางหลักที่แนะนำ (ตัวอย่าง):**

```sql
-- บริษัทลูกค้า (แต่ละองค์กรที่ใช้ beNeCare)
companies (id, name, tax_id, contact_email, contact_phone, line_oa_channel_id, line_oa_channel_secret, line_oa_access_token, line_oa_user_id, is_active, created_at, updated_at)

-- ผู้ดูแลระบบของ beNeCare (ฝั่งเรา)
system_admins (id, email, password_hash, full_name, role, created_at)

-- ผู้ใช้งานในระดับบริษัท (HR / Admin ของลูกค้า)
company_users (id, company_id, email, password_hash, full_name, role, is_active, created_at)

-- พนักงานในองค์กรลูกค้า (ผู้เอาประกันกลุ่ม)
employees (id, company_id, employee_id, first_name, last_name, email, phone, line_user_id, department, position, is_active, created_at, updated_at)

-- คำถามและคำตอบที่ถามบ่อย (FAQ)
faqs (id, company_id, question, answer, category, is_active, sort_order, created_at)

-- ประวัติการสนทนา LINE OA
conversations (id, company_id, line_user_id, employee_id, status, started_at, ended_at)

messages (id, conversation_id, direction, message_type, content, ai_handled, created_at)

-- การแจ้งเตือน broadcast
broadcasts (id, company_id, title, message, target_audience, sent_at, status)

-- การตั้งค่าระบบและเวอร์ชัน
system_settings (id, key, value, description, updated_at)
schema_migrations (id, version, name, executed_at)  -- สำหรับระบบอัปเกรด
audit_logs (id, company_id, user_id, action, entity_type, entity_id, old_value, new_value, created_at)
```

**ข้อกำหนดด้านฐานข้อมูล:**
- ใช้ InnoDB engine, รองรับ transactions
- เพิ่ม index สำหรับ `company_id` ทุกตารางธุรกิจ
- รองรับตัวอักษรภาษาไทย (utf8mb4)
- มีตาราง `schema_migrations` เพื่อติดตามเวอร์ชันโครงสร้างฐานข้อมูล ใช้ร่วมกับระบบอัปเกรด

### 2.3 ผู้ใช้งานและสิทธิการเข้าถึง (RBAC)

| บทบาท (Role) | รายละเอียด | สิทธิหลัก |
|---|---|---|
| Super Admin | ดูแลระบบกลาง beNeCare | จัดการบริษัท, ดูแลระบบตั้งค่า, อัปเกรด, ดู Log ทั้งหมด |
| Company Admin (HR) | ผู้ดูแลของแต่ละบริษัทลูกค้า | จัดการพนักงานในบริษัทตนเอง, ดูรายงาน, ส่ง Broadcast, ตั้งค่า LINE OA เบื้องต้น |
| Company Staff | เจ้าหน้าที่ดูแลลูกค้าของบริษัทลูกค้า | ตอบแชตส่งต่อจาก AI, ดูประวัติการสนทนาของบริษัทตนเอง |
| Employee | พนักงานในองค์กรลูกค้า | ถามคำถามผ่าน LINE OA, ดู Rich Menu, รับ Broadcast |
| End User (LINE OA) | ผู้ใช้ LINE ทั่วไปที่เป็นพนักงานลูกค้า | ส่งข้อความเข้ามาถามคำถามประกันกลุ่ม |

**กฎการแยกข้อมูล:** Company Admin ของบริษัท A มองเห็นเฉพาะข้อมูลของบริษัท A เท่านั้น Super Admin เห็นทุกบริษัทได้

### 2.4 หน้าจอหลักของระบบ (Screens / Pages)

#### A. Installer (ติดตั้งครั้งแรก) — เข้าถึงก่อนล็อกอินครั้งแรก
1. **หน้าต้อนรับ Installer** — ตรวจสอบสภาพแวดล้อม (Node, MariaDB connection, ENV)
2. **ตั้งค่าฐานข้อมูล** — กรอก host, port, database name, username, password ของ MariaDB; ทดสอบการเชื่อมต่อ
3. **สร้างบัญชี Super Admin แรก** — อีเมล, รหัสผ่าน, ชื่อผู้ดูแลระบบ
4. **ตั้งค่าบริษัทแรก** — ชื่อบริษัท, รหัสประจำตัวผู้เสียภาษี, อีเมลผู้ติดต่อ, เบอร์โทร
5. **ตั้งค่า LINE OA เบื้องต้น** — Channel ID, Channel Secret (สามารถข้ามและกลับมาตั้งค่าทีหลังในเมนูการตั้งค่าได้)
6. **สรุปและติดตั้ง** — สร้างฐานข้อมูล, รัน 마이กราชันเบื้องต้น, สร้างบัญชีแอดมิน, เสร็จสิ้น → เข้าสู่หน้าเข้าสู่ระบบ

#### B. Admin Web (ERP-style, หลังบ้านทางการ)
1. **Dashboard** — สรุปจำนวนบริษัท, พนักงาน, จำนวนแชตวันนี้, คำถามที่ถามบ่อย, การแจ้งเตือนที่ค้าง
2. **บริษัท (Companies)** — รายชื่อบริษัทลูกค้า, เพิ่ม/แก้ไข/ปิดการใช้งานบริษัท
3. **ผู้ใช้งานบริษัท (Company Users)** — จัดการ HR/Admin ของแต่ละบริษัท
4. **พนักงาน (Employees)** — รายชื่อพนักงานในบริษัท, ค้นหา, เพิ่ม/แก้ไข/ลบ, ดูสถานะความคุ้มครอง (ข้อมูลพื้นฐานที่ระบบมี)
5. **LINE OA ตั้งค่า** — Channel ID, Secret, Access Token, Rich Menu, ข้อความต้อนรับ, กฎ Auto-reply
6. **คำถามที่พบบ่อย (FAQ)** — จัดการคำถาม/คำตอบ แยกตามบริษัท, หมวดหมู่
7. **ประวัติการสนทนา (Conversations)** — ดูแชตย้อนหลัง แยกบริษัท, ดูว่าข้อความไหน AI ตอบ, ข้อความไหนส่งต่อมนุษย์
8. **ส่งข้อความแจ้งเตือน (Broadcast)** — สร้างข้อความ, เลือกกลุ่มเป้าหมาย (ทั้งบริษัท / แผนก / ทุกบริษัท), กำหนดเวลาส่ง
9. **การตั้งค่าระบบ (System Settings)** — การตั้งค่าทั่วไป, จัดการผู้ดูแลระบบกลาง, **ส่วนอัปเกรดระบบ**
10. **ส่วนอัปเกรดระบบ (Upgrade)** — ดูเวอร์ชันปัจจุบัน, ตรวจสอบเวอร์ชันใหม่, สำรองข้อมูลก่อนอัปเกรด, รันマイกราชัน, แสดงประวัติการอัปเกรด
11. **บันทึกการดำเนินการ (Audit Log)** — ดูประวัติการเข้าสู่ระบบ, การเปลี่ยนแปลงข้อมูลสำคัญ

#### C. LINE OA (ฝั่งพนักงานผู้ใช้งาน)
- **Rich Menu** — ปุ่มเมนูถาวร เช่น "ถามเรื่องประกัน", "คู่มือเคลม", "ติดต่อเจ้าหน้าที่", "ข่าวสารจากบริษัท"
- **ข้อความต้อนรับ** — ตอบอัตโนมัติเมื่อพนักงานเพิ่มเป็นเพื่อนกับ LINE OA
- **Auto-reply / AI Chatbot** — ตอบคำถามเบื้องต้นตลอด 24 ชั่วโมง
- **Human Handoff** — เมื่อ AI ตอบไม่ได้ หรือผู้ใช้พิมพ์ขอคุยกับเจ้าหน้าที่ → ส่งแจ้งเตือนไปยัง Company Staff ใน Admin Web
- **Broadcast รับข้อความ** — รับแจ้งเตือนต่ออายุกรมธรรม์, ข่าวสารสำคัญ

### 2.6 Workflow หลัก (Workflow)

**Workflow 1: ติดตั้งระบบครั้งแรก (First-time Install)**
1. เปิดเว็บไซต์ beNeCare ครั้งแรก → redirect ไป Installer อัตโนมัติ (ถ้ายังไม่มีการตั้งค่า)
2. ผู้ดูแลกรอกข้อมูลเชื่อมต่อ MariaDB → ระบบทดสอบการเชื่อมต่อ
3. สร้างฐานข้อมูลและตารางเริ่มต้นผ่านマイกราชัน
4. สร้างบัญชี Super Admin คนแรก
5. ตั้งค่าบริษัทแรกและ LINE OA (ตัวเลือก)
6. เสร็จสิ้น → เข้าสู่หน้าเข้าสู่ระบบ Admin Web

**Workflow 2: พนักงานถามคำถามผ่าน LINE OA**
1. พนักงานส่งข้อความเข้ามาใน LINE OA (เช่น "เคลมประกันกลุ่มทำยังไง")
2. LINE Webhook ส่งเหตุการณ์มายัง beNeCare backend
3. ระบบตรวจสอบว่า line_user_id ผูกกับพนักงานในบริษัทไหน (หรือยังไม่ได้ผูก → ให้เลือกบริษัทหรือลงทะเบียน)
4. AI วิเคราะห์เจตนาคำถาม → ค้นหาคำตอบจาก FAQ ของบริษัทนั้น
5. ถ้า AI ตอบได้และมั่นใจ → ส่งคำตอบกลับผ่าน LINE
6. ถ้า AI ตอบไม่ได้ หรือผู้ใช้พิมพ์ "คุยกับเจ้าหน้าที่" → สถานะแชตเปลี่ยนเป็น "รอเจ้าหน้าที่" → แจ้งเตือน Company Staff ใน Admin Web → スタッフตอบผ่าน Admin Web หรือ LINE

**Workflow 3: อัปเกรดระบบ (ในส่วนการตั้งค่า)**
1. Super Admin เข้าเมนูการตั้งค่า → ส่วนอัปเกรดระบบ
2. ระบบแสดงเวอร์ชันปัจจุบัน และตรวจสอบเวอร์ชันใหม่ (จากไฟล์ manifest หรือไฟล์อัปเดตที่เตรียมไว้)
3. ก่อนอัปเกรด ระบบแนะนำให้สำรองข้อมูล MariaDB (มีปุ่มสำรองข้อมูล)
4. ผู้ดูแลยืนยันการอัปเกรด → รันマイกราชันฐานข้อมูลตามเวอร์ชันเป้าหมาย → อัปเดตไฟล์ระบบ → แสดงผลสำเร็จหรือล้มเหลว พร้อมบันทึกในประวัติการอัปเกรด

**Workflow 4: HR จัดการพนักงานใน Admin Web**
1. Company Admin ล็อกอิน → เลือกบริษัทตนเอง
2. เข้าเมนูพนักงาน → ดูรายชื่อ, ค้นหา, เพิ่มพนักงานใหม่ (กรอกรหัสพนักงาน, ชื่อ, อีเมล, เบอร์, LINE user id)
3. แก้ไขหรือปิดการใช้งานพนักงานที่ลาออกแล้ว
4. การเปลี่ยนแปลงทั้งหมดบันทึกใน Audit Log

## 3. แยกชัดเจน — สิ่งที่ต้องยืนยันกับ AIA (ยังห้ามสร้าง)

ส่วนนี้สำคัญมาก **ห้ามให้ AI หรือทีมพัฒนาสร้างฟังก์ชันหรือการเชื่อมต่อใดๆ ในส่วนนี้ขึ้นมาเอง** จนกว่าจะมีเอกสารยืนยันจาก AIA เป็นลายลักษณ์อักษร

### 3.1 รายการที่ยังต้องยืนยันกับ AIA

| รายการ | รายละเอียด | สถานะ |
|---|---|---|
| การเชื่อมต่อ API กับ AIA | ตรวจสอบกรมธรรม์, สถานะเคลม, เบี้ยประกัน ผ่าน API ของ AIA | ⏳ รอยืนยัน |
| การใช้โลโก้และชื่อ AIA | แสดงโลโก้ AIA ในหน้าเว็บ, สื่อประชาสัมพันธ์, หน้าเข้าสู่ระบบ | ⏳ รอยืนยัน |
| SSO / Single Sign-on | เข้าสู่ระบบ beNeCare ด้วยบัญชีของ AIA | ⏳ รอยืนยัน |
| การดึงข้อมูลผู้เอาประกัน | นำเข้าข้อมูลพนักงานจากระบบ AIA มาใน beNeCare | ⏳ รอยืนยัน |
| การส่งข้อมูลเคลมไปยัง AIA | ส่งคำขอเคลมหรือเอกสารสนับสนุนไปยังระบบ AIA | ⏳ รอยืนยัน |
| การใช้ชื่อ domain แบรนด์ AIA | เช่น care.aia.co.th หรือ subdomain ที่เกี่ยวข้อง | ⏳ รอยืนยัน |

### 3.2 ข้อกำหนดให้ AI
- เมื่อเขียนโค้ด ให้เตรียม **จุดต่อขยาย (extension point / interface)** สำหรับการเชื่อมต่อ AIA ในอนาคต เช่น `AIAAdapter` interface แต่ **ไม่ต้องเขียน lógica การเรียก API จริงของ AIA**
- ห้ามฮาร์ดโค้ด endpoint, API key, หรือข้อมูลรับรองของ AIA ลงในโค้ด
- ห้ามสร้างหน้าจอที่อ้างว่า "เชื่อมต่อกับ AIA แล้ว" จนกว่าจะได้รับการยืนยัน
- ในเอกสารและหน้า UI ให้ใช้คำว่า "พร้อมเชื่อมต่อกับ AIA (ภายหลัง)" แทนการแสดงสถานะว่าเชื่อมต่อแล้ว

## 4. AI ฟีเจอร์และ LINE OA (รายละเอียดเพิ่มเติม)

### 4.1 ความสามารถของ AI
- **Intent Classification**: แยกว่าคำถามเกี่ยวกับอะไร (ความคุ้มครอง, การเคลม, เอกสาร, ต่ออายุ, อื่นๆ)
- **FAQ Matching**: ค้นหาคำตอบจากตาราง FAQ ของบริษัทนั้น โดยใช้ความหมายเชิงลึก (semantic search) หรือคีย์เวิร์ด
- **Confidence Score**: ถ้า AI มั่นใจต่ำกว่าเกณฑ์ที่ตั้งไว้ (เช่น 70%) ให้ส่งต่อมนุษย์แทนการเดาตอบ
- **ภาษาไทย**: รองรับภาษาไทยเป็นหลัก เนื่องจากผู้ใช้และ HR เป็นคนไทย

### 4.2 LINE OA รายละเอียดทางเทคนิค
- ใช้ LINE Messaging API ผ่าน Webhook (ต้องเปิดใช้ Webhook ใน LINE Developers Console)
- ต้องเก็บ `Channel Access Token` และ `Channel Secret` อย่างปลอดภัย (encrypt ตอนจัดเก็บในฐานข้อมูล หรือใช้ environment variable)
- รองรับ Rich Menu (เมนูถาวรด้านล่างแชต LINE)
- รองรับการส่งข้อความแบบ Push (ส่งถึงผู้ใช้คนเดียว) และ Broadcast (ส่งถึงหลายคน)
- เวลาตอบกลับผ่าน Webhook ต้องตอบภายใน 20 วินาที ตามข้อกำหนดของ LINE

## 5. ความปลอดภัย (Security) และ PDPA

| ด้าน | มาตรการ |
|---|---|
| การยืนยันตัวตน | Login ด้วยอีเมล + รหัสผ่าน (hash ด้วย bcrypt/argon2), รองรับ session หรือ JWT |
| การอนุญาต | RBAC ตามบทบาท (Super Admin, Company Admin, Company Staff, Employee) |
| การแยกข้อมูล | ทุกตารางธุรกิจมี `company_id` ทุกคำถาม SQL กรองด้วย `company_id` เสมอ |
| การเข้ารหัส | ข้อมูลเดินทางผ่าน HTTPS (TLS), รหัสผ่าน hash, ข้อมูลละเอียดอ่อน encrypt ที่ rest (ตัวเลือกตามเฟส) |
| Access Token LINE | เก็บเป็นความลับ ไม่แสดงในหน้า UI แบบ plain text เต็ม ต้องควบคุมการเข้าถึง |
| บันทึกการเข้าถึง | Audit Log บันทึกว่าใคร ทำอะไร กับข้อมูลอะไร เมื่อใด |
| PDPA (ไทย) | เก็บข้อมูลส่วนบุคคลเฉพาะที่จำเป็น มีหน้าลบข้อมูล / ถอนความยินยอม (ตัวเลือกเฟสแรก, แนะนำให้เตรียมไว้) |
| การสำรองข้อมูล | ก่อนอัปเกรดระบบ ต้องมีตัวเลือกสำรองฐานข้อมูล MariaDB |

## 6. ระบบ Installer และการอัปเกรด (รายละเอียดเฉพาะ)

### 6.1 Installer (ครั้งแรกที่ติดตั้ง)
- ตรวจจับอัตโนมัติว่าเป็นการติดตั้งครั้งแรกหรือไม่ (เช็คจากไฟล์ `.env` ที่มีค่าครบถ้วน และตารางฐานข้อมูลมีอยู่หรือไม่)
- ถ้ายังไม่ติดตั้ง → redirect ไปหน้า Installer โดยอัตโนมัติ
- ขั้นตอน: ตรวจสอบสิ่งแวดล้อม → ตั้งค่า MariaDB → สร้างฐานข้อมูล/ตาราง → สร้าง Super Admin → ตั้งค่าบริษัท → ตั้งค่า LINE OA → เสร็จสิ้น
- หลังติดตั้งเสร็จ → ลบหรือปิดการเข้าถึง Installer (หรือให้เข้าถึงได้เฉพาะ Super Admin ผ่านการยืนยันตัวตน)

### 6.2 ส่วนอัปเกรดในเมนูการตั้งค่า
- อยู่ในหน้า System Settings → "อัปเกรดระบบ"
- แสดงเวอร์ชันปัจจุบันของระบบ (อ่านจากไฟล์เวอร์ชันหรือ environment variable)
- ตรวจสอบเวอร์ชันใหม่ (เปรียบเทียบกับไฟล์ manifest ที่เตรียมไว้ หรือตรวจสอบด้วยตนเอง)
- ก่อนอัปเกรด: แสดงปุ่ม "สำรองข้อมูลฐานข้อมูล" (export MariaDB เป็นไฟล์ SQL)
- รันマイกราชัน: อ่านไฟล์マイกราชันที่ยังไม่ได้รัน จากตาราง `schema_migrations` → รันตามลำดับ → บันทึกเวอร์ชันใหม่
- แสดงสถานะ: สำเร็จ / ล้มเหลว / ดำเนินการอยู่ พร้อมข้อความผิดพลาดถ้ามี
- บันทึกทุกการอัปเกรดในตารางประวัติการอัปเกรด (พร้อมวันที่, ผู้ดูแลที่ทำ, เวอร์ชันก่อนและหลัง)

## 7. เกณฑ์ตรวจรับงาน (Acceptance Criteria)

### 7.1 ติดตั้งระบบ (Installer)
- [ ] เปิดเว็บครั้งแรกแล้วเข้าสู่ Installer อัตโนมัติ (เมื่อยังไม่ได้ตั้งค่า)
- [ ] สามารถทดสอบการเชื่อมต่อ MariaDB ก่อนติดตั้งได้
- [ ] สร้างฐานข้อมูลและตารางเริ่มต้นสำเร็จ
- [ ] สร้าง Super Admin คนแรกสำเร็จ และเข้าสู่ระบบได้
- [ ] ตั้งค่าบริษัทและ LINE OA ได้ (หรือข้ามแล้วกลับมาตั้งค่าทีหลังได้)
- [ ] หลังติดตั้งเสร็จ เข้าสู่หน้าเข้าสู่ระบบ Admin Web ได้

### 7.2 ผู้ใช้งานและสิทธิ
- [ ] Super Admin login แล้วเห็นทุกบริษัท Company Admin login แล้วเห็นเฉพาะบริษัทตนเอง
- [ ] Company Admin ของบริษัท A มองเห็นข้อมูลพนักงานและแชตของบริษัท B ไม่ได้
- [ ] บทบาท Company Staff สามารถตอบแชตที่ส่งต่อจาก AI ได้เฉพาะบริษัทตนเอง

### 7.3 LINE OA
- [ ] พนักงานส่งข้อความเข้ามาใน LINE OA แล้วได้รับการตอบกลับภายใน 20 วินาที (กรณี AI ตอบ)
- [ ] Rich Menu แสดงถูกต้องบนแอป LINE มือถือ
- [ ] ข้อความต้อนรับส่งเมื่อผู้ใช้เพิ่มเป็นเพื่อนกับ LINE OA
- [ ] เมื่อ AI ตอบไม่ได้ ระบบแจ้งเตือน Company Staff ใน Admin Web

### 7.4 AI
- [ ] AI ตอบคำถามจาก FAQ ของบริษัทนั้นได้ถูกต้อง (ทดสอบด้วยคำถามอย่างน้อย 10 คำถามต่อบริษัท)
- [ ] AI ส่งต่อมนุษย์เมื่อถูกถามคำถามนอกขอบเขต FAQ หรือผู้ใช้ขอคุยกับเจ้าหน้าที่

### 7.5 การอัปเกรด
- [ ] หน้าตั้งค่าระบบแสดงส่วนอัปเกรดระบบได้
- [ ] แสดงเวอร์ชันปัจจุบันได้ถูกต้อง
- [ ] สำรองข้อมูลฐานข้อมูลก่อนอัปเกรดได้ (มีไฟล์สำรองออกมา)
- [ ] รันマイกราชันอัปเกรดฐานข้อมูลสำเร็จ และบันทึกประวัติการอัปเกรด

### 7.6 ความปลอดภัย
- [ ] รหัสผ่านผู้ใช้ถูกเก็บในรูปแบบ hash เท่านั้น ไม่ใช่ plain text
- [ ] Audit Log บันทึกการเข้าสู่ระบบและการเปลี่ยนแปลงข้อมูลสำคัญ
- [ ] การเข้าถึงหน้า Admin ต้องล็อกอินก่อนเสมอ

### 7.7 ประสิทธิภาพ (เบื้องต้น)
- [ ] รองรับบริษัทลูกค้าอย่างน้อย 20 แห่ง และพนักงานรวมสูงสุด 5,000 คนในระยะเริ่มต้น
- [ ] หน้า Dashboard โหลดภายใน 3 วินาที
